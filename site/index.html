An AI site reliability engineer that asks first.

Site Reliability Clanker keeps a cloud application deployed, patched and backed up. It finds the work, writes each change as a pull request, and explains it in plain language. A person approves. Only then does it get access: for that one change, for seconds.

A working prototype. It runs end to end on a local cluster today.

The problem

Most of operations is maintenance, and most maintenance is late.

The work never ends.

A Kubernetes version reaches its end of support. A base image gets a CVE. The database has a patch. The backups need a restore test. Each job is small. Together they are a full-time job that nobody has the time for.

Automation with standing access is a standing risk.

A pipeline or an agent that can change production at any time is a credential that works at 03:00, for anybody who holds it. Give an AI that credential, and you have made the risk larger and less predictable.

The person who approves cannot read the plan.

The people who are accountable for a change are often not the people who can read four hundred lines of infrastructure diff. So they approve what they do not understand, or they slow everything down.

Clanker lets a language model do the reading and the writing. Plain code and a person do the deciding.

What it does

It does the operations work that a small team has no time for.

You give Clanker an application and a target. It deploys the application, and then it looks after it. For each job below, it finds the work, prepares the change and asks you. It does not wait for a ticket.

Deploys from a blank slate

It builds the network, the Kubernetes cluster, the database, the storage and the application, layer by layer, from OpenTofu code in your repository.

Ships releases

It sees a new release, opens the pull request and applies it after approval. A canary check then tests the result. If the check fails, it rolls the release back.

Keeps you patched

It watches for security fixes, database patches and Kubernetes versions that come to their end of support, and proposes each upgrade before it is late.

Protects the data

It runs backups and database maintenance on a schedule. It also runs restore drills, so you know that the backups can be restored.

Finds drift

If somebody changes production by hand, it finds the difference and opens a pull request to put it right.

Responds to incidents

It reads the logs and the recent changes, writes a diagnosis and proposes a runbook. Policy code decides if that runbook can run without a person.

How it works

Every change takes the same seven steps.

The language model does the reading and the writing. It has no credential and no tool that applies a change. Plain code and a person make each decision.

  1. Code

    Detect

    Detectors watch for new releases, security fixes, versions near their end of support, schedules, drift and failing requests.

  2. Model

    Draft

    The model writes the change as a pull request in your infrastructure repository. That is all it can do.

  3. Code

    Plan and rate

    The runner makes an OpenTofu plan. Policy rules read the plan and set the risk tier, T0 to T3. The model does not rate its own work.

  4. Model

    Explain

    The model writes the approval page in plain language. The counts, the names and the tier come from the plan, and the model cannot change them.

  5. Person

    Approve

    A notice goes out by email and chat. A person decides in the dashboard or the phone app. The riskiest changes need two people.

  6. Code

    Apply

    The access broker issues a signed grant for one layer. The runner applies exactly the plan that was approved. The grant is revoked when the job ends.

  7. Code

    Verify

    A canary check tests the result and rolls back on failure. Each step is a record in a hash-chained audit log.

Why you can trust it

Five rules decide almost everything else.

Each rule is short. Under each one is what it did in the scripted month.

  1. 1

    The model proposes. Code decides.

    The language model drafts changes, summaries and answers. It never rates its own risk, never holds a cloud credential, and has no tool that applies a change.

    In the scripted month Policy code set the tier of all 7 rated changes.

  2. 2

    Every change is a pull request.

    No console clicks and no ad-hoc kubectl. Even “restart that deployment” is a recorded runbook job with parameters.

    In the scripted month 6 pull requests and 5 runbook jobs. The one change made by hand was found by the drift check and put back through a pull request.

  3. 3

    What was approved is exactly what runs.

    An approval is bound to a commit and to the hash of a saved plan. If the world moved, the apply is refused and the change comes back for approval.

    In the scripted month Each of the 12 applies ran the plan hash that was approved.

  4. 4

    No standing write access.

    Read-only by default. Write permission exists for one approved job, for the one layer that the job touches, and is revoked when the job ends.

    In the scripted month 18 grants in 29 days. Write or debug access existed for 3 min 27 s in total. The longest grant lasted 67 s.

  5. 5

    Multi-cloud is a contract, not a port.

    One interface, four implementations (AWS, Google Cloud, Azure and a local target), and one conformance suite for all of them.

    In the scripted month The local target ran this whole month. The AWS, Google Cloud and Azure stacks are validated against the same contract and are not applied yet.

What an approver sees

Decide in less than a minute. Or read down to the raw plan.

The approval page starts with one sentence: what changes, and why now. Then the impact, the risk tier and the rule that set it, what changes, how it is made safe, and which permission the change asks for. The model writes the words. The counts, the names and the tier come from the plan and from policy code, and the model cannot change them.

Questions that the agent must answer well

  • What is waiting on me, and what happens if I leave it for a week?
  • Are we behind on any patches? Which ones matter?
  • What changed in production in the last 30 days, and who approved each change?
  • When was the last successful restore test?
  • Why did the upgrade last night take longer than planned?
  • What does the agent have access to right now?

The test application

A business that rents out live fish.

Clanker needs something real to look after. The month above used Paperboat: customers rent a fish, a driver delivers it, and a driver collects it when the rental ends.

It has a live inventory board, fish that age and retire, deliveries, and a support desk for people whose fish looks at them strangely. Under that, it needs what every business application needs: a database, a shared file system, a load balancer, and releases that sometimes go wrong.
