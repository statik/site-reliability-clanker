Ship an AI site reliability engineer with your product instead of an installer.

S.R.C. (Site Reliability Clanker) installs, upgrades, patches, and monitors your product. It writes each change as a pull request, a person approves, and it gets access only for that one change.

Try it on your laptop ↓ Watch the video ↓

A working prototype. It runs end to end on a local cluster today.

The problem

You sell software that your customers run themselves.

So you build an installer. Then upgrades. Then patches.

A Kubernetes version reaches its end of support. A base image gets a CVE. The database has a patch. The backups need a restore test. None of this work is your product, and it does not end.

Every customer runs them a little differently, and a little late.

The steps are run by hand, by people who have other work, in an environment that you cannot see. No two installations are in the same state.

Late patches turn into outages and security incidents.

An upgrade that waits for a quiet week waits for months. The fix existed, and the installation did not have it.

The answer

Don’t build an installer. Ship an AI site reliability engineer with your product.

It installs, upgrades, patches, and monitors your product. For each job below, it finds the work, prepares the change and asks. It does not wait for a ticket.

Deploys from a blank slate

It builds the network, the Kubernetes cluster, the database, the storage and the application, layer by layer, from OpenTofu code in your repository.

Ships releases

It sees a new release, opens the pull request and applies it after approval. A canary check then tests the result. If the check fails, it rolls the release back.

Keeps you patched

It watches for security fixes, database patches and Kubernetes versions that come to their end of support, and proposes each upgrade before it is late.

Protects the data

It runs backups and database maintenance on a schedule. It also runs restore drills, so you know that the backups can be restored.

Finds drift

If somebody changes production by hand, it finds the difference and opens a pull request to put it right.

Responds to incidents

It reads the logs and the recent changes, writes a diagnosis and proposes a runbook. Policy code decides if that runbook can run without a person.

The convenience of managed services, without a third-party contract.

How it works

Setup is a single download. Then every change takes the same three steps.

The download walks you through logging in to your cloud provider and sets up the control plane. The control plane then deploys your product, layer by layer. After that, it keeps the product up to date like this.

  1. It finds the work and writes the change.

    It finds the needed maintenance without someone having to manually ask for it: a new release, a security fix, drift. Each maintenance step is a version-controlled Infrastructure as Code changeset.

  2. Code rates the risk, and a person approves.

    Code rates the risk of the change. The model has no say in that. A person reads a plain summary of what will change, and approves. Routine, low-risk work runs under a standing approval that a person signed once.

  3. It gets access for that one change.

    Permissions are narrowly scoped, and issued only for that approved change. They are revoked as soon as the job ends. Then it checks the result, and rolls back if the check fails.

S.R.C. uses AI to understand and propose the change as deterministic code. An adversarial review then challenges the risk level, and a strict policy engine decides which changes a person must approve.

Why you can trust it

Five rules decide almost everything else.

Each rule is short. Under each one is what it did in the scripted month.

  1. 1

    The model proposes. Code decides.

    The language model drafts changes, summaries and answers. Fixed rules set the risk tier from the plan itself. A second model can raise that tier and can never lower it. The model that wrote the change has no say in its tier, holds no cloud credential, and has no tool that applies a change.

    In the scripted month Policy code set the tier of all 7 rated changes.

  2. 2

    Every change is a pull request.

    No console clicks and no ad-hoc kubectl. Even “restart that deployment” is a recorded runbook job with parameters.

    In the scripted month 6 pull requests and 5 runbook jobs. The one change made by hand was found by the drift check and put back through a pull request.

  3. 3

    What was approved is exactly what runs.

    An approval is bound to a commit and to the hash of a saved plan. If the world moved, the apply is refused and the change comes back for approval.

    In the scripted month Each of the 12 applies ran the plan hash that was approved.

  4. 4

    No standing write access.

    Read-only by default. Write permission exists for one approved job, for the one layer that the job touches, and is revoked when the job ends.

    In the scripted month 18 grants in 28 days. Write or debug access existed for 1 min 53 s in total. The longest grant lasted 27 s.

  5. 5

    Multi-cloud is a contract, not a port.

    One interface, four implementations (AWS, Google Cloud, Azure and a local target), and one conformance suite for all of them.

    In the scripted month The local target ran this whole month. The AWS, Google Cloud and Azure stacks are validated against the same contract and are not applied yet.

What an approver sees

Decide in less than a minute. Or read down to the raw plan.

The approval page starts with one sentence: what changes, and why now. Then the impact, the risk tier and the rule that set it, what changes, how it is made safe, and which permission the change asks for. The model writes the words. The counts, the names and the tier come from the plan and from policy code, and the model cannot change them.

Questions that the agent must answer well

  • What is waiting on me, and what happens if I leave it for a week?
  • Are we behind on any patches? Which ones matter?
  • What changed in production in the last 30 days, and who approved each change?
  • When was the last successful restore test?
  • Why did the upgrade last night take longer than planned?
  • What does the agent have access to right now?

Slack and Teams

Slack and Teams tell the right people. The approval page is where they decide.

Each approval request goes to the approvers by email, Slack, Microsoft Teams and Discord. The message states the facts of the change and links to the approval page. Nobody approves from a chat message. The person signs in to the dashboard, where the plan, the tier and the explanation are.

Routine work asks once.

Routine maintenance is tier T1. It runs under a standing approval that a person signed once. A T2 change asks one approver. A T3 change can ask for a second approver.

The routes are a file in a repository.

A route names the events, the channels, the audience and the urgency: at once, or in one digest. Failures and incidents go to the operators. Debug access and the inference spend cap go to the admins.

Facts only.

A message holds the summary, the work item, the tier, the rule and the number of approvers. The text passes the secret scrubber first.

Slack and Teams get the message through an incoming webhook. In the runs of the prototype the messages went to a local webhook sink, not to a real workspace (see Live screens). Quiet hours, escalation and threads are not built.

Cost and runbooks

The model works when a runbook is written, not each time it runs.

A runbook is a fixed script in a repository. The prototype has four: restart a deployment, back up the database, run a restore drill, and maintain the database. Each run is the same script with new parameters, so the result is predictable and a run needs no inference.

The model selects. It does not write commands.

After an incident, the model can propose one runbook from a list. Code checks the name and the target against that list. If one of them is not on it, the work stops and a person decides.

A person signs first.

A runbook runs only under a standing approval that an approver or an admin signed. Each run is tier T1, is a record in the audit log, and gets its own grant for 15 minutes.

A model for each role, and a daily cap.

The Explainer uses a smaller model. The Author and the Investigator use a larger one. The control plane adds up the cost of the model calls of the day. At 5 US dollars it stops the calls for that day and writes an audit record. Each call is stored with its role, model, tokens and cost.

Evals

Evals measure each role before you trust it.

The suite has nine tasks on Inspect AI. Eight test the model roles with the live models. One tests the tier policy and calls no model. A task passes a run only if every check passes. Inference is now one of the core ingredients of a modern application stack, alongside storage, memory, and compute. Your product should get better and easier to manage when new models come out.

The model of each role is one setting. Each eval task runs against a named model, so you can measure a new model before a role uses it. Nothing changes the model by itself today: a person changes the setting.

The test application

A business that rents out live fish.

S.R.C. needs something real to look after. The month above used Paperboat: customers rent a fish, a driver delivers it, and a driver collects it when the rental ends.

It has a live inventory board, fish that age and retire, deliveries, and a support desk for people whose fish looks at them strangely. Under that, it needs what every business application needs: a database, a shared file system, a load balancer, and releases that sometimes go wrong.
