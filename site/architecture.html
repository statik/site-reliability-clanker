Architecture

How maintenance work is discovered, put on the backlog, and how risk is managed for each step of a change.

Paperboat is the workload. The platform is the infrastructure as code that the agent edits. S.R.C. is the control plane: a dashboard, an agent, a policy engine, a runner, an access broker, a git forge and an audit log. A simulator makes a month pass in minutes.

Figure 1

A change, from detection to the audit record.

S.R.C. finds the needed maintenance without someone having to manually ask for it: new releases, security fixes, versions near their end of support, and drift between the running system and the code. Each change is infrastructure as code in a pull request, so it can be reviewed and reproduced. Before anything is applied, a plan records exactly what will change, and that plan is what a person approves. The privileges are separate: the model writes and explains, policy code sets the risk, a person approves, and only the runner applies, with a credential for one layer that ends with the job.

On AWS, the core of the control plane is a Nanos unikernel on one virtual machine in an auto scaling group, in your own private network. Its state is in a managed PostgreSQL database. Each job runs in a short-lived runner.

Figure 4

The model proposes. Code decides.

The security boundary is the set of tools that each role has. The model can write a pull request. It has no tool that applies one, so the worst that a confused or manipulated model can do is open a pull request, which a person then sees with a tier that policy assigned.

Proposes and explains

The language model

  • Drafts the infrastructure change as a pull request
  • Writes the approval summary in plain language
  • Answers questions, with links to the evidence
  • Diagnoses an incident under a read-only debug grant
  • Rate the risk of its own change
  • Hold a cloud credential
  • Merge, approve or apply

Decides and executes

Deterministic code

  • Detects what is due: releases, advisories, drift, failing health
  • Assigns the risk tier from the plan, by policy
  • Requires the approvals that the tier demands
  • Mints and revokes the credential for each job
  • Applies exactly the plan whose hash was approved
  • Verifies with a canary, and rolls back when it fails

Risk tiers

Four tiers, assigned from the plan, never by the model.

TierMeaningExamplesApproval
T0Read-onlyDetectors, diagnostics, questions and answersNone
T1Routine and reversibleRestart a deployment, verify a backup, vacuum the databaseA standing approval that a person signed once. Each use is logged
T2Normal changeAn application release, a database patch, a parameter changeOne approver
T3High riskAnything that replaces or destroys stateful resources; network or identity changesTwo approvers and a maintenance window
